# BUG-001 — A transaction added while a filter is active vanishes without feedback

**Severity:** Medium
**Frequency:** Always
**Component:** Ledger — filter + create
**Environment:** Chrome 141, macOS 26, demo app `demo/server.mjs`
**Status:** Open

## Preconditions

- Signed in, ledger showing at least one income and one expense

## Steps to reproduce

1. Set the **Show** filter to `Income`
2. Fill the form with type `Expense`, amount `50000`, note `Coffee`
3. Click **Add**

## Expected

Either the new row is shown (the filter clears, or the new row is pinned above the
filtered list), or an explicit message says the row was added but is hidden by the
current filter.

## Actual

The form clears — which reads as success — and the new row is not visible. No message
explains why. Switching the filter to `All` reveals the row was created.

## Evidence

Reproducible by hand; the form-clears-but-row-is-absent sequence is also covered by
`tests/specs/regression/transactions.spec.ts` (TC-11 clears the form after save).

## Impact

The user believes the save failed and submits again. Because every submit carries a fresh
`Idempotency-Key`, the retry creates a second row — so a misleading empty state turns into
a data-integrity defect.

## Hypothesised cause

`addTransaction()` calls `loadTransactions()` with the filter still applied, so the
newly created row is filtered out of the response. The UI treats "reload succeeded" as
"the user can see their new row".
